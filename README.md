# phanthymotus-modelhub

On-robot model serving for [PhanthyMotus](https://github.com/4paradigm/phanthymotus):
large models (LLM first, then VLM and others) running **on the robot's own
accelerator**, exposed over an OpenAI-compatible HTTP API.

> **Status: skeleton + first card (LLM via vLLM).** Unit-tested; end-to-end on
> Jetson Thor in progress. Models other than Qwen3 0.6B have not been measured on
> Thor yet — their memory budgets in `models.yaml` are estimates.

## Where it sits

PhanthyMotus has four on-robot components. This is a fifth, alongside them:

| Component | Repo | Does |
|---|---|---|
| Drivers | `phanthymotus-driver` | MCP servers for physical devices |
| Perception | `phanthymotus/perception` | ASR, TTS, vision — streaming, in-process models |
| Agent Core | `phanthymotus/agent-core` | LLM agent loop, canvas, dashboard — **CPU only** |
| ActuCore | `phanthymotus/actucore` | Execution layer, including local VLA |
| **ModelHub** | **this repo** | **Request/response serving of large models on the robot** |

Agent Core already talks to any LLM through a list of `{url, key, model}` entries
and an OpenAI client. A ModelHub endpoint is just one more entry:

```
{"url": "http://127.0.0.1:<port>/v1", "key": "local", "model": "<model>"}
```

So Agent Core stays a small CPU application, and local and cloud models sit behind
the same interface — it does not know which one it is talking to.

## Layout

```
modelhub/
  main.py              MCP bundle (port 15740) + starts the gateway; registers with agent-core
  config.yaml          ports, model/state directories, per-card settings
  models.yaml          built-in model registry (generated by tools/pin_model.py)
  plugins/
    llm.py             the LLM card: tool declaration + actions
    llm_workbench.html its ops page, hosted by agent-core's workbench
  serving/             shared by every card (future VLM cards reuse it)
    gateway.py         unified OpenAI-compatible endpoint (port 15741), routes by `model`
    vllm_engine.py     one `vllm serve` process: start, health, logs, stop
    registry.py        model rows: ModelScope source, pinned revision, size + SHA256 per file
    downloads.py       download queue: resume, pause, cancel, verify
  tools/pin_model.py   generate a registry row from ModelScope
  Dockerfile.jetson    FROM jetson-base:jp72-vllm
  deploy/service.yml   compose fragment shipped in the image
  tests/
deploy/build_modelhub.sh
```

Two planes:

- **Data** — Agent Core's LLM client calls `http://127.0.0.1:15741/v1` directly.
  The gateway routes by `model` to the engine on an internal loopback port,
  relays streams chunk by chunk, aborts the backend when the client disconnects,
  and answers `503 model_not_ready` while a model is loading.
- **Management** — the `llm` card (type `actuator`) opens an ops page
  (`x-workbench`): pick a model, download, load/unload with a memory budget,
  logs, a test prompt. Only `info` is exposed to the LLM.

### Where things are kept

Everything ModelHub persists lives under one directory on the shared model
volume — nothing that must survive a container rebuild stays in the container:

```
/opt/embodied/models/modelhub/        (/models/modelhub in the container)
  models/<id>/   weights; downloads stage here and are renamed into place
  state/         llm.json (selected model, budget, autoload), models.user.yaml
  cache/         vLLM / inductor / triton compile caches
```

The model service does **not** follow the canvas project: `start`/`stop` only
report state, and the container reloads the last selected model on boot.

## Adding a model

A model is a row in `models.yaml`, not code:

```
python3 modelhub/tools/pin_model.py Qwen/Qwen3-8B-FP8 --id qwen3-8b-fp8 \
    --title "Qwen3 8B (FP8)" --memory-gb 20 --max-model-len 32768 \
    --tool-call-parser hermes --reasoning-parser qwen3
```

The row pins the repo's HEAD commit and every file's size and SHA256. The ops
page's "添加模型" does the same at runtime and writes to
`/models/modelhub/state/models.user.yaml`.

`memory_gb` is converted to vLLM's `--gpu-memory-utilization`. On Jetson that
fraction is of the **whole unified memory**, which perception, Agent Core and
the OS share; vLLM's default 0.9 would starve them. The budget covers only what
vLLM accounts for on the GPU side; the process itself takes about 4.4 GB more
(measured on Thor: a 6 GB budget cost 9.8 GB of MemAvailable), so the ops page
shows budget + `host_overhead_gb`, and that sum is what is capped at 90%.

Selecting a model that is not on disk downloads it first and then loads it —
from the ops page, and on boot for the remembered selection. While it does, the
card's `info` is `state: loading` with a progress `message`
("正在下载模型 'X' … 40% (…)"), which Agent Core shows live in the
project-start dialog.

## Build and deploy

Follows phanthymotus's infrastructure: `deploy/build_modelhub.sh` sources
`phanthymotus/deploy/build_common.sh` from a sibling checkout (or
`PHANTHYMOTUS_DIR`) and reads registry credentials from its `deploy/.env`.

```
./deploy/build_modelhub.sh --mirror tuna           # JetPack 7.2
```

Image: `<registry>/phanthy-motus/modelhub:release.<YYMMDD>.<sha>-jetson-jp7.2`.
Deploy through the console, or for a throwaway test on the target:
`curl -fsSL https://motus.phanthy.com/run-pr-image.sh | bash -s -- <image>`.

### Base image

`jetson-base:jp72-vllm` is NVIDIA's NGC vLLM container, re-hosted in TCR
unchanged (pulling nvcr.io from the robots runs at ~130 KB/s):

```
D=$(docker buildx imagetools inspect nvcr.io/nvidia/vllm:26.10-py3 --raw \
    | python3 -c "import sys,json;print([m['digest'] for m in json.load(sys.stdin)['manifests'] if m['platform']['architecture']=='arm64'][0])")
docker buildx imagetools create -t bj-warehouse.tencentcloudcr.com/phanthy-motus/jetson-base:jp72-vllm nvcr.io/nvidia/vllm@$D
```

Registry-to-registry, nothing unpacked locally. Run it on the VPC build host;
retry on a dropped upload, already-pushed layers are skipped.

## Why a separate component

- **Different runtime shape.** Perception loads models into its own process and
  works on streaming ROS topics. An LLM server is a standalone process with its own
  scheduler (continuous batching, KV cache).
- **Different image and release cadence.** Inference engines bring their own large
  CUDA stack. Folding one into the perception image couples two release cycles
  and invites the shared-runtime conflicts perception has already hit.
- **Not the execution layer.** ActuCore drives the robot and is gated as such;
  a language model server is not an actuator.

## Boundary with `phanthymotus-cloud`

Split by **where the model runs and who owns the resource contention**, not by
"is it inference":

- **ModelHub (here):** models on the robot. They compete with perception for the
  same unified memory and GPU, so the memory budget is a robot-side decision.
- **phanthymotus-cloud:** models in a machine room. Throughput, cost, autoscaling,
  API keys and billing live there.

## What this repo owns — and does not

| Owns | Does not own |
|---|---|
| Packaging an upstream engine (vLLM / TensorRT-LLM / llama.cpp) for each target | Writing an inference engine |
| Model manifests, weight download and checksum | Billing, API key issuance |
| Memory budget alongside perception | The agent loop |
| Warmup and health gating (ready only after the model is loaded) | Robot actuation |
| OpenAI-compatible endpoint; optional status/switch-model hook for the dashboard | |

Name things after the role, not after one model class or one framework — the same
service will host VLMs and embeddings too.

## First target: Jetson Thor T4000

| | |
|---|---|
| JetPack | 7.2.1 (L4T R39.2.1, Ubuntu 24.04) |
| CUDA / TensorRT | 13.2 / 10.16 |
| Memory | 59 GB unified (CPU + GPU + perception share it) |

Engines must be Thor (CUDA 13) builds; Orin JetPack 5/6 images do not apply.

## Open questions

1. **Engine.** vLLM is the first engine. Whether its NGC build (CUDA 13.4 user
   space) runs on Thor's 13.2 driver is being verified on the device.
2. **Memory budget.** Entered as GB per model (see above). The right numbers per
   model on Thor alongside perception are still to be measured.
3. **Local-first routing in Agent Core.** Agent Core currently sends each request to
   **all** live endpoints at once and takes the first answer. With a local and a
   cloud entry configured, every turn hits both. "Local first, cloud as fallback"
   needs a change there.
